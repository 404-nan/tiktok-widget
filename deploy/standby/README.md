# ライコネの待機機と一時起動

## 公開 URL を維持する待機機

LuLServer を正本のままにして、別の Linux 機が SSH で差分を取りに行きます。待機中にアプリや TikTok 接続を起動しません。事前に本番と同じ版・依存ライブラリを入れ、同期データを持たせておくので、障害時に GitHub や npm へ取りに行く必要はありません。無料の手持ちホストか Always Free VM を使えますが、停止する AI サンドボックスは訓練用で、常時稼働の待機機には数えません。

| ファイル | 用途 |
| --- | --- |
| `standby.sh` | 待機版準備、定期同期、外部監視、昇格 |
| `standby-route.mjs` | スナップショットの検査、外部の HTTP 確認、Cloudflare DNS 切替 |
| `setup.sh` | アプリ・トンネルの起動と停止。待機版を準備し、昇格時にはインストール済みの版を起動 |

### 一度だけ準備

1. 本番とは別の、利用者データを置いてよい永続ホストを用意します。専用ユーザー・暗号化された永続ディスク・権限 `0700` の `STANDBY_DIR` を使い、バックアップを公開しません。待機側から本番へ、ホスト鍵を確認済みの SSH 接続を作ります。自動同期には同期元の Git の HEAD と指定のデータを読める、待機用の非対話接続を使います。本番へ常駐ジョブは追加しません。
2. [Cloudflare Zero Trust](https://one.dash.cloudflare.com/) で**本番とは別の**待機専用トンネルを作ります。待機トンネルの ingress に公開ホスト名 → `http://127.0.0.1:3939` を設定しますが、その時点で**既存の公開 DNS は変更しません**。別の確認用ホスト名にもこのトンネルを設定し、`^/help/standby-[0-9a-f-]+\.txt$` だけを転送、それ以外は 404 にします。確認用ホスト名の DNS は待機トンネルを指すプロキシ付き CNAME にします。公開・確認用 URL のヘルス確認パスはキャッシュ対象から外します。同じ待機トンネルを別の機械と共有しません。
3. 待機機のリポジトリで `bash deploy/standby/standby.sh prepare` を実行します。既定は 1.4.2。版更新時は `REF=<本番の完全なコミットID>` で再準備します。最初に別の検証用ドメインと架空データで同期から昇格まで通し、本番 DNS の切替は配信がない時に別途許可を取ります。

| 設定（待機機の環境変数） | 意味 |
| --- | --- |
| `PRIMARY_SSH`, `PRIMARY_DIR` | 同期元の SSH ホスト（必要なら `user@host`）。ディレクトリ既定は `/home/lul/tiktok-widget` |
| `STANDBY_DIR`, `PORT` | 待機機の保存先（既定は `~/.local/share/tiktok-widget-standby`）とポート（既定は 3939、トンネル設定と揃える） |
| `PUBLIC_HOST`, `STANDBY_PROBE_HOST` | 現在の公開ホスト名と別の確認用ホスト名。`https://` は不要 |
| `CF_ZONE_ID`, `CF_DNS_RECORD_ID` | 公開ホストのある Cloudflare ゾーンと既存プロキシ付き CNAME の ID |
| `PRIMARY_TUNNEL_ID`, `STANDBY_TUNNEL_ID` | 本番と待機専用トンネルの UUID |
| `CF_API_TOKEN`, `TUNNEL_TOKEN` | 昇格時にだけシークレットから渡す。DNS API トークンは該当ゾーンの DNS 編集だけに絞る |
| `MAX_SNAPSHOT_AGE` | 昇格できるデータの最大経過秒数。既定は 900 秒 |
| `STANDBY_NOTIFY_COMMAND` | 任意。通知を受ける実行ファイルの絶対パス。状態が変わった時だけ診断要約を引数に1個渡す |

待機機のスケジューラで `bash deploy/standby/standby.sh sync` を5分おき、`bash deploy/standby/standby.sh watch` を1分おきに稼働させます。作業ディレクトリ・設定はスケジューラにも渡し、標準エラーを監視します。監視は公開先の HTTP と同期の鮮度を確認し、昇格・再起動はしません。通知が失敗すると15秒以内で止め、次回再試行します。`status` は同期の経過秒数と版を表示します。

同期は `data/` と `config.yaml`（配信者別モードでは任意）だけを取り、ローカルバックアップ・作業中の一時ファイル・リンクはコピーしません。転送は最大約2 MiB/秒、無通信30秒・全体240秒で打ち切り、失敗しても前の正常コピーを維持します。2世代はファイル単位のコピーであり、複数ファイルを同時点に固定したバックアップではありません。待機機が昇格したら旧本番からの同期は停止します。

### 障害時の切替と復旧

1. 配信していないことを確認し、**旧本番のアプリとトンネルを止めて、復電・DNS 復旧でも自動で書き込みを再開できない状態にします**。SSH が使えない時は、電源遮断などで書き込みを止められた証拠が必要です。ヘルスチェックの失敗だけではこの確認になりません。
2. 待機機で `bash deploy/standby/standby.sh promote --primary-fenced`。鮮度・版・旧本番の公開停止・待機機固有の応答を確認してから、既存の CNAME だけを待機専用トンネルへ向けます。通常、OBS の URL 差し替えは不要ですが、WebSocket は再接続します。前回同期以降の変更や、停止中に届いたイベントは戻るとは限りません。
3. DNS を更新した後の確認に失敗した時は、自動で戻しません。待機側の書き込みを残して同じコマンドで再確認します。同期が古い時は既定で拒否されます。最新のコピーが本当に取れない場合、欠ける時間を確認した責任者だけが `MAX_SNAPSHOT_AGE` を明示的に引き上げて判断します。
4. 復帰は別作業です。配信がない時に待機側を停止・書き込み遮断し、待機側の更新を退避し、本番バージョンと整合するデータを本番へ戻して疎通確認後に CNAME を戻します。古いデータの LuLServer をそのまま立ち上げないでください。既存の昇格済みディレクトリは残し、待機をやり直す時は新しい専用ディレクトリで準備します。

フロントだけを別ホストに置いても、配信画面と管理画面は同じ URL の API・WebSocket に依存するため、バックエンド障害は消えません。まず URL と書き込み先を一つに保ち、2台の同時書き込みや有料ロードバランサーは使いません。

## 検証用または緊急の一時起動

本番ホストが止まった間だけ、Manus などの Debian / Ubuntu 系 Linux 機（x86_64・arm64）で使う手順です。公開先を切り替える前に、元のホストで配信中のライコネが動いていないことを確認してください。

- `setup.sh`: ライコネを本番と同じ hosted モードで起動し、Cloudflare Tunnel で公開します。systemd は使わず、機械が動いている間はプロセスが落ちても起こし直します。

```bash
curl -fsSL https://raw.githubusercontent.com/404-nan/tiktok-widget/dev/standby-host/deploy/standby/setup.sh | bash
```

- 既定は本番の 1.4.2（`e2a303d`）。版を変えるときは右側を `REF=<版やブランチ> bash` にします。待ち受けは `127.0.0.1:3939`（確認用には `PORT` を変更可能）。
- 配信者・設定・履歴を引き継ぐ場合は、**最初の起動前**に、最上位に `data/` と任意の `config.yaml` があるバックアップを用意します。手元の tar.gz は右側を `DATA_TARBALL=/path/to/backup.tar.gz bash` にします。保護された HTTPS のダウンロード先なら `DATA_URL` でも渡せます。バックアップを一般に公開したり、ダウンロードの鍵をチャットに貼ったりしないでください。同じ保存先の `data/` があるときは上書きしません。
- 一時 URL は最後に表示され、`~/.local/share/tiktok-widget-standby/url.txt` に保存されます。トンネルが起動し直すと URL は変わります。決まったドメインを使うときは Cloudflare 側で公開先を `http://127.0.0.1:3939` に設定し、`TUNNEL_TOKEN` を秘密の環境変数として渡します。その場合は表示に従い、自分で公開側の `/healthz` も確認します。元のホストと同じトンネルを同時に動かさないでください。
- 合言葉のファイル・ログは起動先に残り、停止方法は起動後に表示されます。停止は `bash ~/.local/share/tiktok-widget-standby/run.sh stop`。停止してもデータは消えません。端末を閉じても動きますが、機械が停止・再起動したときは起動コマンドを実行し直します。
- `DATA_URL` はダウンロード用プロセスの引数やログには出しません。
- 停止時は Cloudflare に処理中の通信を終えるための5秒を渡します。停止の合図から約8秒経っても残るプロセスは強制終了し、ライコネ本体の停止も試します。
