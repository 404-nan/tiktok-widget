# バージョンとお知らせのルール（ライコネ）

製品のバージョンと、配信者に見える「アップデートのお知らせ」の決め事。
作るものには必ずバージョンを付け、本番に出すたびに「何ができるようになったか」「何を直したか」が
配信者に伝わる状態にするためのルール。

## バージョンの正本

- **正本は `package.json` の `version` 欄、1か所だけ。** ほかの場所にバージョンの数字を書かない。
- 画面表示と API は `src/version.js` 経由でそこから読む（ダッシュボード下部の表示と `GET /api/announcements` の `version`）。
- `package-lock.json` の `version` は npm が触るもので、製品バージョンとはみなさない。

## 採番（SemVer）

`MAJOR.MINOR.PATCH` の3つの数字で付ける。

| 上げる数字 | どういう変更か | 例 |
|---|---|---|
| PATCH（いちばん右） | 不具合の修正だけ | 1.0.0 → 1.0.1 |
| MINOR（まんなか） | 新しくできることが増えた（今までの使い方は壊れない） | 1.0.1 → 1.1.0 |
| MAJOR（いちばん左） | 今までの使い方・設定がそのまま使えなくなる変更 | 1.1.0 → 2.0.0 |

MINOR を上げたら PATCH は 0 に、MAJOR を上げたら MINOR と PATCH は 0 に戻す。

### 基本は細かく刻んで、パッチを小まめに進める

- 変更は大きなひとかたまりにせず、細かく分けて出す。そのたびにパッチを1つ進める（1.0.1 → 1.0.2 → 1.0.3 …）。
- マイナーは「新しくできることが増えた」と言える時だけ、メジャーは下の「大台の決め方」にある節目の時だけ上げる。どちらか迷ったら、小さい方（パッチ）を選ぶ。
- パッチの数字が細かく進むこと自体が「直し続けている」表示になるので、パッチを惜しまない。

## 大台（MAJOR）の決め方

MAJOR は「お客さんの体験が一段変わる節目」にだけ付ける。数字を上げること自体を目的にしない。

### 大台にしていい変更

- 画面の全面刷新（ダッシュボードの見た目・使い勝手がまるごと変わる）
- 本命機能の登場（製品の中心になるような大きな機能）
- 使い方の大きな変更（今までの手順や設定の前提が変わる。採番表の「そのまま使えなくなる変更」はここに含む）

このどれでもない変更は、規模が大きく見えても MINOR か PATCH で出す。

### 内部の作り直しは大台に溜めない

- コードの整理・作り直し（リファクタリング）は、お客さんから見えないので大台の理由にしない。
- 溜めて一気に入れると壊しやすいので、平常時のリリースに小さく刻んで入れる。その回に上げる数字は PATCH か MINOR で足りる。

### 大台を出す前の段取り

1. 現行版の安定を先に固める。分かっている不具合は、大台の前に直し切る。
2. 事前に伝える。何がどう変わるかは、運営のお知らせ（`src/notes.js` 側、ダッシュボードの「更新のお知らせ」に出る）や `docs/news/` で先に知らせる。`src/announcements.json` は「出したものだけを書く場所」なので、事前告知には使わない。
3. 出したら、そのバージョンのお知らせとして announcements に「何が変わったか」を顧客向けの言葉で書く。

## リリースの手順（本番に出すたびに必ず）

1. バージョンを上げる（上の採番どおり）。バージョンを上げていない変更は本番に出さない。
2. `src/announcements.json` の**先頭**に、今回のリリースのお知らせを1件以上足す（下の形式）。
3. この2つは、リリースの変更と同じマージに含める（バージョンだけ先行・後追いはしない）。
4. 反映は従来どおり `rc/` ブランチへ入れて、自動デプロイの関門を通す。

## rc ブランチとの関係

- `rc/YYYY.MM.DD-N` は「本番に出す候補を固める枝」の名前で、**日付とその日の通し番号**。製品バージョンとは別物で、対応づけはしない。
- 製品バージョンはあくまで `package.json` の SemVer。1回の本番反映が、1つのバージョンに対応する。
- 初期バージョンは **1.0.0** とする（お客様への正式提供を始めた時点の状態）。開発中に使っていた 0.x 系の番号は、ここで切り替える。
- 最初のバージョン付きリリースは **1.0.1**（「使う」を押したあとの画面が崩れる不具合の修正）。

## お知らせの形式（src/announcements.json）

配列で、新しいものを先頭に置く。各エントリの項目：

| 項目 | 内容 |
|---|---|
| `version` | その変更が入る製品バージョン（`package.json` と同じ数字） |
| `date` | リリース日（`YYYY-MM-DD`） |
| `type` | `new`（新機能）／ `fix`（修正）／ `add`（追加）のどれか |
| `title` | 何ができるようになったか・何を直したかが一目で分かる見出し |
| `body` | 配信者向けの説明。敬語で、平易な言葉で書く |

### 文言の決め事

- お客様（配信者）向けなので**敬語**で書く。
- 技術用語（API の名前・ファイル名・commit・内部の仕組み）は出さない。「何ができるようになりました」「何を直しました」が伝わる書き方にする。
- まだ本番に出ていないものは書かない。「出ます」「近日」とも書かない（出したものだけを書く場所）。
- ダッシュボードでは新しいものから3件まで表示される。古いものもデータには残る。

### ほかの「お知らせ」との違い

- `src/notes.js` のお知らせは、運営がその場で書く連絡用（置き場所は実行時データ）。製品の履歴はこちら（announcements）で持つ。
- `docs/news/` は月ごとの説明文書、`CHANGELOG.md` は開発者向けの内部履歴。配信者の画面に出るのは announcements だけ。
