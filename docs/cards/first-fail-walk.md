# first-fail-walk: 初めての配信者が失敗したときの道を、開発用の画面で歩く
for: 北極星
仕事の種類: 調べる(読み取りのみ)
見た目が変わるか: 変わらない

なぜ要るか: first-run-walk(docs/reviews/first-run-walk-2026-11-03.md)は、うまくいく道だけを歩いて「止まる」は0件だった。初めての人が離れるのは失敗したときの方が多いはずなのに(推測)、その道は誰も歩いていない。北極星は1人のまま。
前提: kind-ui の使う人は、パソコンが苦手で LIVE Studio を使う配信者。開発 3940 と本番 3939 は触らない。作業場所のコードを空いた番号(3961 など)と一時のデータの場所で起動する。外の TikTok につなぎにいかない形で歩けない失敗は、コードを読んだ範囲だけ書き、「歩いていない」と書く。
目的: 失敗したときに配信者が止まる場所を、実際の画面で1つ選び、次に直すカードを絞る。

## 触ってよいファイル
- `docs/reviews/first-fail-walk-2026-11-04.md`
- 写真はリポジトリに入れない。`/tmp/first-fail-walk/` に置く。
コードと設定は変えない。外への通信、DM、投稿、再起動はしない。本物の配信者のデータは読まない。

## 完成の条件
- AC-1 空のデータで起動した画面を、幅390と幅1280で、次の4つの失敗で歩く。(a) TikTok のユーザー名を間違えて入れる、または空のままにする (b) 配信していないのに配信の接続を始める (c) 配信ソフトに貼る URL の一部を欠いて、ブラウザで開く (d) ためす前にウィジェットを全部消す。失敗ごとに、画面に出た文をそのまま書き、kind-ui の4つの問いのうち「何が起きたか分かるか」「次に何を押すか分かるか」に はい/いいえ で答え、写真のパスを書く。
- AC-2 何も出ない・内部の言葉が出る(英語のエラー、コード、「接続エラー」だけ)ものは、ファイル:行を添えて全部書く。言葉は docs/words.md と比べる。
- AC-3 見つけた問題に、止まる/迷う/細かい の3段階を付ける。止まる=説明なしだと次にすることが分からない。「止まる」が無ければ無いと書く。
- AC-4 最後に、次に直す1つを選び、理由とそのカードの完成の条件を書く。実物で確かめられない推測は「推測」と書く。利用が増えない原因とは断定しない。
- AC-5 人の名前、ID、鍵を報告に書かない。

## 証拠
報告と写真。別のレビュー役が、報告の手順で同じ画面を開き、「止まる」とした問題が本当に起きるかを確かめる。
