# レビュー: ingest 

レビュー結果です。`npm test` は 302 件すべて緑でした。`artifacts/shots/` はありません（このカードは画面なしなので問題ではありません）。
**カードを満たしていない**
- `test/ingest-keys.test.js` がありません。カードの「証拠」に挙がっていて、差分にもありません。
- AC-8(b) で `kind: 'comment'` の重複判定が効きません。直接接続のイベントは `chat` で登録されます（`src/ingest.js:34`）。受け口側は `comment` のまま照合します（`src/ingest.js:86`）。fingerprint の先頭が `chat|…` と `comment|…` で食い違い、必ず外れます。`chat` で送ったときだけ効きます。
- AC-6 で `username`（@ハンドル）が使われないことがあります。`uniqueId = userid || username` なので（`src/ingest.js:73`）、両方来ると @ハンドルが捨てられます。先頭の `@` も取っていません。
- AC-9 の「瞬間 40 回」は最初の1回しか使えません。トークンは空になったときしか補充されません（`src/ingest.js:116-124`）。たとえば 15 個残った状態でしばらく止めても 15 個のままで、次の連続送信は 15 回目で 429 になります。
- AC-9 の 16KB 制限は `content-length` ヘッダーだけを見ています（`src/ingest.js:61`）。ヘッダーの無い送信は、`express.json` の既定 100KB まで通ります。また、本文の解析が鍵の照合より先に走ります。壊れた JSON は日本語でない Express 標準のエラーになります。
**既存機能への影響**
- `server.js` の `express.urlencoded` はアプリ全体に掛かります。`/in` 以外の既存ルートも、フォーム形式の本文を解析するようになります。
- `byIngestKey`（`src/tenants.js`）は、鍵が違うリクエストでも全配信者の `runtime()` を作ります。鍵なしで誰でも叩ける入口なので、止めている配信者の runtime まで作られ、負荷とメモリが増えます。
**カードに無い変更**
- `server.js` で、止められた配信者（`enabled: false`）の owner 鍵が `/api/ingest` を使えるようにしています。カードにも AC にもありません。既存の「止めたら全部 403」の動きが変わります。
**テストが弱い**
- AC-8(b) のテストは `chat` だけで、`comment` のすり抜けを検出できません。
- `eventId` が10分で期限切れになること、1000件で古いものから消えることは確かめていません。
- 15秒・20秒の境目も確かめていません。
- 受け口の `test=true` を、AC-10 の「本番の数を汚さない」の観点で確かめていません。実装では、テスト送信も `accepted` と `byKind` に数えています。
- 作り直し前後の `ingest.json` 書き込み失敗は、テストにありません。
**本番で起きそうな問題**
- `src/ingest.js:34` の `this.events`（重複判定の記録）は消されません。直接接続のイベントごとに増え続けるので、長時間の配信やコメントの多い配信でメモリが増え続けます。
- 違う鍵への総当たりには、回数制限がありません。鍵は 192 ビットなので当たる心配はありませんが、1回ごとに上の `runtime()` の問題が起きます。
実行したのは `npm test` と読み取りだけで、コードは変更していません。
