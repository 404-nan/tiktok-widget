# レビュー: ingest 2巡目

**問題あり**
**カードを満たしていない**
- `test/ingest-keys.test.js` がまだありません。カードの「証拠」にあります。1巡目のレビューでも指摘されていましたが、直っていません。
- AC-20 の実装が間違っています。`server.js` の `if (!tenant.enabled)` の中で、owner 鍵の `POST /api/ingest/key` を特別扱いしています。止められた配信者でも新しい受け口の鍵を作って保存し、その全文を 403 の本文で返します。カードは「今までどおり 403」で、何も実行しない前提です。
  - 止められた配信者の鍵が作られ、`ingest.json` に書かれます。
  - 鍵の全文が 403 の応答に出ます。
  - テスト (`ingest-round2.test.js:154`) はステータスしか見ないので、この挙動を検出できません。
**既存機能を壊していそうな箇所**
- 上の特別扱いは runtime とは別の `IngestKeyStore` に書きます。すでに作られている runtime の `ingest.keys` はメモリ上の古い内容のままです。
  - 止められた配信者を再開したあと、その鍵で `/in/<鍵>` を呼ぶと、`byIngestKey` は通ります。
  - ところが `Ingest.handle` の `accepts` が古い内容と比べるので、再起動するまで 404 のままです。
  - `GET /api/ingest` の `keyHint` も古いままです。
**カードに無い追加や変更**
- 上記の止められた配信者の鍵作成が、カードに無い変更です。
- `server.js` で `express.json()` を `/in` 以外にだけ掛ける形にしました。これは AC-17 のために必要で、カードの範囲内です。
**テストが弱い**
- AC-20 のテストは、鍵が作られていないこと、本文に鍵が出ていないことを確かめていません。
- 時間の境目 (15秒・20秒・10分・1000件) のテストが引き続き見当たりません。
- `test=true` のテスト送信も `accepted` と `byKind` に数えます。AC-10 の「本番の数を汚さない」との関係を確かめるテストはありません。
- `test/helpers/guard-harness.js` の流儀に沿っているかは確認していません。
**本番で起きそうな問題**
- `byIngestKey` は、鍵が違うリクエストでも全配信者の `ingest.json` を読みます。`IngestKeyStore.load()` の中で `chmodSync` も毎回走ります。回数制限は鍵の照合より後にあるので、配信者が増えると、鍵なしで叩ける入口がディスクを読み続けます。
- 受け口は `eventId` の長さや `giftId` の長さを切りません。`likeCount` も上限がありません。1回の本文は 16KB までなので影響は小さいです。
`npm test` は 310 件すべて通りました。`artifacts/shots/` はありません。このカードは画面なしなので問題ではありません。コードは変更していません。
