# レビュー: ingest 3巡目

問題があります。
**カードを満たしていない**
- `test/ingest-keys.test.js` がありません。カードの「証拠」にある、鍵の保存の単体テストです。要約だけが保存されること、0600、作り直しで前の鍵が死ぬことを確かめるものです。受け入れテストが一部を間接的に見ているだけです。
- `src/ingest.js:107` の `body == null` で応答を返さずに戻っています。本文が JSON の `null` だと `JSON.parse` が `null` を返し、応答が一切返りません。接続が開いたままになります。AC-17 は壊れた JSON に日本語1行の 400 を返すことを求めています。
- `src/ingest.js:128` で `username` が `@` だけのときに `userId` へ落ちません。`'@'` は真と判定され、`@` を取ると `uniqueId` が空になります。`userId` も来ていれば、AC-15 の「空にならない」を満たしません。
**カードに無い追加や変更**
- `server.js` の `ingestRequest` に、鍵が `'null'` か `'undefined'` のときの専用 403 があります。カードにありません。AC-4 の「違う鍵は 404」からも外れます。
- 次のカードの `docs/cards/ingest-status.md` と `ingest-euler-ws.md`、およびレビュー記録 `docs/reviews/` が、この差分に入っています。この仕事の範囲外です。
- `server.js` のグローバルな `express.json()` を、リクエストごとに `express.json()` を作り直す書き方に変えています。既存ルートへの影響は小さいですが、毎回パーサーを生成します。
**本番で起きそうな問題**
- `src/ingest.js:73-79` で、`content-length` が無く本文が 16KB を超えると、`continue` で最後まで読み続けます。長さの上限なしに接続を保持します。16KB を超えた時点で打ち切るべきです。
- `src/tenants.js` の `byIngestKey` は、違う鍵が来るたびに全配信者について `statSync` と sha256 の再計算をします。鍵の照合前には送信回数の上限がありません。配信者が増えると、無認証の連打が CPU とディスクの負荷になります。
- 本文を読み終えてから 429 を判定しています。有効な鍵を持つ側が 16KB を連打すると、制限前に毎回読み込みが走ります。
- `src/ingest.js` の `pruneDirect` は、直接の接続のイベントごとに全記録を走査します。いいねは内容が毎回違うため、記録が増えやすいです。大きな配信では O(n²) になります。
- `tenants.ingestKeys` は、配信者を削除しても消えません。
